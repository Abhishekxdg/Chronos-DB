What happens, step by step

An agent is asked to "mark every customer inactive for 90 days as churned". It works through MCP, where it can read anything but can only change a copy it made. You approve in the shell.

  1. Agent
    Tries the change on the real table. 
    refused: changes need branch="<a branch you forked>". Call fork first
  2. Agent
    Forks its own copy, a world called churn-cleanup. Nothing is copied, so it takes microseconds.
  3. Agent
    Runs one statement in its world. 
    update customers set status = 'churned' where last_active < current_date - 90
UPDATE 1240
  4. Agent
    Tries to merge it. 
    refused: agents can't merge. A person reviews your diff and merges it
  5. You
    Read what changed, row by row. 
    $ chronos mydb diff churn-cleanup
1240 changes on churn-cleanup
~ customers/2  status: "active" -> "churned"
  6. You
    Approve it. 
    $ chronos mydb merge churn-cleanup
merged 1240 changes from churn-cleanup into main
  7. You
    Change your mind. Undo puts back exactly the rows the merge changed and keeps everything else. 
    $ chronos mydb undo
undid the merge of churn-cleanup into main: put back 1240 rows

Try it on one of your tables

Copy one Postgres table in. Your database isn't touched: the copy is a file on your machine.

Export the rows

Plain CSV from psql.

psql -c "\copy customers to 'data.csv' csv header"

Export the columns

Running chronos import with no arguments prints the exact psql command for the column list.

psql --csv -t -c "select …" > schema.csv

Import, then point your agent at it

The whole import succeeds, or you get the line and column that failed.

chronos import mydb customers data.csv --schema schema.csv
